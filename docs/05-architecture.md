## 1. الهدف والمبادئ

**الهدف:** هيكل بسيط يناسب مطوّرًا منفردًا، لكنه صارم بما يكفي ليحمي ثلاثة أشياء: **الخصوصية، والصلاحيات، وقابلية الاختبار.**

| المبدأ | المعنى العملي |
|---|---|
| **الطبقات بوضوح** | كل طبقة لها مسؤولية واحدة، واتجاه الاعتماد واحد (من الأعلى للأسفل) |
| **القرار في مكان واحد** | القواعد في `services`، والصلاحيات في `policy`، والاستعلامات في `repositories` |
| **لا اعتماد على HTTP خارج طبقته** | الخدمات لا تعرف `Request` ولا `Response` ولا رموز HTTP |
| **كل شيء قابل للاختبار** | الوقت والبريد والتخزين تُحقن، فتُستبدل في الاختبارات |
| **الأمان بالبنية** | البنية نفسها تمنع الأخطاء الشائعة (تسريب حقول، تجاوز صلاحيات، SQL مدمج) |
| **البساطة** | لا حاويات حقن معقدة، ولا CQRS، ولا أحداث، ولا مكتبات "للمستقبل" |
| **لا اختراع** | مكتبات قياسية ومجرّبة، وأنماط FastAPI المعتادة |

## 5. الطبقات ومسؤولياتها

### 5.1 الجدول الأساسي

| الطبقة | مسؤوليتها | **ممنوع** فيها |
|---|---|---|
| **`routers`** | استقبال HTTP: التحقق (عبر schemas)، استدعاء الصلاحيات، تفويض خدمة واحدة، تشكيل الاستجابة | قواعد العمل، استعلامات، `if role == ...` مبعثرة |
| **`schemas`** | شكل الطلب والاستجابة، التحقق من الحقول، التطبيع (الهاتف) | المنطق، الوصول لقاعدة البيانات |
| **`services`** | **قواعد العمل**، التنسيق بين المستودعات والصلاحيات والتخزين والبريد والتدقيق | `Request`/`Response`، رموز HTTP، SQL مباشر، `commit` |
| **`repositories`** | استعلامات SQLAlchemy فقط | قواعد العمل، الصلاحيات، `commit` |
| **`models`** | تعريف الجداول والقيود والعلاقات | أي منطق عمل |
| **`policy`** | قرارات الصلاحية والنطاق والشروط | الوصول لقاعدة البيانات (تتلقى ما تحتاجه من الخدمة) |
| **`core`** | الإعدادات والأمان والأخطاء والتسجيل والوقت | الاعتماد على الطبقات العليا |
| **`storage` / `mail`** | واجهات خارجية خلف تجريد | قواعد العمل |
| **`cli`** | أوامر خارج HTTP، تستدعي الخدمات نفسها | منطق مكرّر (يُستدعى من الخدمات) |

### 5.2 قواعد الاعتماد (اتجاه واحد)

```
web/routers ──┐
              ├──► services ──► repositories ──► models
api/routers ──┘       │
   │                  ├──► policy
   │                  ├──► storage / mail / clock
   │                  └──► core
   └──► schemas
```

| القاعدة | الفحص |
|---|---|
| `models` لا يستورد من أي طبقة أعلى | اختبار معماري |
| `repositories` يستورد `models` و`core` فقط | اختبار معماري |
| `services` **لا** يستورد من `api` ولا `web` ولا `fastapi` | اختبار معماري |
| `api/routers` و`web/routers` **لا** يستوردان `repositories` ولا `models` مباشرة | اختبار معماري |
| `policy` لا يستورد `repositories` | اختبار معماري |
| لا استيراد دائري | أداة التدقيق |

> **اختبار معماري:** ملف اختبار صغير يفحص الاستيرادات ويفشل عند أي خرق. هذا أرخص وسيلة لإبقاء البنية سليمة مع مرور الوقت (أو مع مساعد برمجي يكتب الكود).

## 6. مسار الطلب (رحلة كاملة)

مثال: **مشرف يضيف متبرعًا** (`POST /api/v1/supervisor/donors`).

```
1. Middleware     : يولّد request-id، يفحص Origin، يضبط ترويسات الأمان
2. deps           : يحمّل الجلسة والمستخدم، يتحقق من is_active، يفحص CSRF
3. deps           : require(donor:create)  ← صلاحية الدور + MFA إن لزم
4. schemas        : يتحقق من الجسم (حقول زائدة تُرفض، الهاتف يُطبَّع)
5. router         : يستدعي DonorService.create(user, data)
6. service        :
                    ├─ policy: النطاق S (موقعه) والحالة L (حملة جارية)
                    ├─ قواعد الموافقات (06): الهاتف يتطلب موافقة، إلخ
                    ├─ idempotency: معرّف العميل
                    ├─ repository: يحفظ السجل
                    └─ audit: يسجّل donor.create
7. dependency     : يثبّت المعاملة (commit) عند النجاح، يلغيها عند الخطأ
8. router         : يحوّل النتيجة إلى schema الاستجابة (بلا حقول سرية)
9. Middleware     : يضيف الترويسات، ويسجّل الطلب
```

**عند الخطأ:** خدمة ترمي استثناءً نطاقيًا (`PhoneRequiresConsent`) ← `error_handlers` يحوّله إلى الاستجابة الموحّدة ورمزها (04، القسم 3).

## 7. الصلاحيات في البنية

### 7.1 أين يُفحص ماذا

| الفحص | أين | لماذا هناك |
|---|---|---|
| جلسة صالحة، حساب نشط | `api/deps.py` | يلزم قبل أي شيء |
| **صلاحية الدور** (`donor:create`) | `api/deps.py` عبر `require(...)` | يعلنها كل مسار صراحةً |
| **MFA** (M) و**التأكيد الحديث** (R) | `api/deps.py` | تتبع الجلسة، لا البيانات |
| **النطاق** (S): المورد في موقعه | `services` عبر `policy` | يحتاج بيانات المورد |
| **حالة الحملة** (L): جارية | `services` عبر `policy` | يحتاج بيانات الحملة |
| الاستعلام المفلتر بالموقع | `repositories` (يستلم الموقع من الخدمة) | **تُفلتر في الاستعلام نفسه** |

### 7.2 مكونات `policy`

| الملف | المحتوى |
|---|---|
| `permissions.py` | قائمة رموز الصلاحيات (`donor:create`، `campaign:end`...) كما في `03`، القسم 11 |
| `matrix.py` | **المصدر الوحيد** لمن يملك ماذا: دور ← مجموعة صلاحيات |
| `rules.py` | `can(user, permission, resource=None)` والشروط (S، L، M، R) |

**قاعدة:** مصفوفة `03` ومصفوفة `matrix.py` يجب أن تتطابقا، **واختبار المصفوفة الآلي** (انظر 14) يقرأ من `matrix.py` ويتحقق من السلوك الفعلي لكل مسار.

### 7.3 قاعدة 404 مقابل 403

الخدمة ترمي `NotFound` للمورد خارج النطاق (لا `Forbidden`)، فلا يُكشف وجوده. و`Forbidden` تُستعمل لمسارات معروفة بلا صلاحية للدور.

### 7.4 كشف المسارات غير المحمية

اختبار آلي يمر على كل مسارات التطبيق المسجّلة، ويتأكد أن كلًا منها إمّا في **قائمة المسارات العامة المصرّح بها** أو يعلن صلاحية. مسار جديد بلا إعلان **يكسر البناء**.

## 8. المخططات (Schemas) وتسريب الحقول

| القاعدة | التفصيل |
|---|---|
| **ثلاثة أنواع** لكل كيان | `...In` (الإنشاء)، `...Update` (التعديل)، `...Out` (الاستجابة). لا مخطط واحد للكل |
| **`extra = forbid`** على كل مخطط دخول | الحقول الزائدة أو المحجوزة تُرفض (`unknown_field`) |
| **`response_model` على كل مسار** | لا يُرجَع كائن نموذج مباشرة أبدًا |
| **لا حقول سرية في `...Out`** | `password_hash`، `totp_secret_enc`، `token_hash`، `registered_by` للعموم، `ip_hash` |
| **مخططات منفصلة بحسب الجمهور** | `DonorListItemOut` (بلا هاتف) ≠ `DonorDetailOut` (بهاتف) ≠ `HeroOut` ≠ `EmergencyDonorOut` |
| **التطبيع في الـ Schema** | الهاتف: أرقام عربية-هندية ← لاتينية، حذف الفراغات والشرطات، فحص النمط |
| **التحقق المتكرر مقصود** | قواعد الموافقات في Pydantic **و**الخدمة **و**قيد القاعدة (ثلاث طبقات) |
| **التصنيف** | `schemas/common.py` يحوي الأنواع المشتركة (الهاتف، الفصيلة، صفحة النتائج، الخطأ) |

3. **إعادة ترميز كاملة** تُسقط كل البيانات الوصفية (EXIF).
4. تصغير الضلع الأطول (~1600 بكسل).
5. اسم الملف **يولّده الخادم**، ولا اسم من العميل.

## 16. وسطاء (Middleware) والأمان على مستوى التطبيق

**الترتيب (من الخارج للداخل):**

1. **Request ID:** يولّد المعرّف أو يقبله من وسيط موثوق.
2. **عنوان IP الموثوق:** يُؤخذ من ترويسة الوسيط العكسي **فقط** إن كان الطلب قادمًا من وسيط معرَّف في الإعدادات، وإلا يُهمَل (منعًا لتزوير العنوان وتجاوز المعدل).
3. **ترويسات الأمان:** CSP، HSTS، `X-Content-Type-Options`، منع التضمين، سياسة المُحيل.
4. **فحص Origin وCSRF** لطلبات الكتابة المصادَق عليها.
5. **ضغط وحدود الحجم:** حد أقصى لحجم الجسم (JSON وmultipart).

**أسس إضافية:**
- **CORS:** غير مفعّل (نطاق واحد). أي طلب من أصل آخر يُرفض.
- **حدود الجسم:** JSON صغير، والصور حتى 5 ميغابايت.
- **مهلة الطلبات** معقولة.
- **ترويسات التخزين المؤقت** تُضبط في الـ router بحسب `04`، القسم 5.

## 26. ملخص

- **الطبقات:** `web/routers` و `api/routers` ← `services` ← `repositories` ← `models`، مع `policy` و`core` و`schemas` حولها.
- **اتجاه اعتماد واحد** يُفحص باختبار معماري يفشل عند أي خرق.
- **القرار في مكان واحد:** القواعد في `services`، والصلاحيات في `policy`، والاستعلامات في `repositories`، والأخطاء في استثناءات نطاقية بمعالج واحد.
- **الأمان بالبنية:** `extra=forbid`، `response_model` دائمًا، النطاق يُشتق من المستخدم، `autoescape` مفعّل، CSP صارمة بلا سكربتات مضمّنة.
- **المعاملة لكل طلب**، والخدمات لا تُثبِّت.
- **الخدمات الخارجية خلف تجريد** (تخزين، بريد، وقت، معدل) فتُختبر بلا شبكة.
- **الاختبارات البنيوية:** المصفوفة، وتغطية المسارات، وتطابق الأخطاء، والاعتماد المعماري، واختبارات قوالب الويب (`tests/web/`).
- **أنماط ممنوعة** و**تعريف اكتمال** و**وصفة إضافة ميزة** تُرشد العمل بأمان.
