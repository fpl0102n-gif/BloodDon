## 3. التشغيل المحلي (من الصفر)

### 3.1 الخطوات

```
1. استنساخ المستودع
2. تثبيت الاعتمادات من ملف القفل            →  uv sync
3. نسخ ملف الإعداد                          →  cp .env.example .env
4. توليد الأسرار وملؤها في .env             (القسم 4.3)
5. تشغيل قاعدة البيانات (حاوية)             →  docker compose up -d db
6. تطبيق الهجرات                            →  uv run alembic upgrade head
7. إنشاء أدمن أول                           →  uv run python -m app.cli create-admin
8. (اختياري) بيانات تجريبية                 →  uv run python -m app.cli seed
9. تشغيل الخادم                             →  uv run uvicorn app.main:app --reload
10. فحص الصحة                               →  GET http://localhost:8000/health  و  /ready
```

### 3.2 ما يجب أن تراه
- `/health` ← `200` (الخادم حي).
- `/ready` ← `200` (الاتصال بالقاعدة سليم).
- `/docs` متاحة في `dev` فقط.
- البريد في التطوير **لا يُرسَل فعليًا**، بل يظهر في الطرفية أو في أداة التقاط البريد (القسم 6).

## 4. متغيرات البيئة

### 4.1 المبادئ

1. المصدر الوحيد للإعدادات: **متغيرات البيئة** (تُقرأ في `core/config.py`).
2. **لا قيم افتراضية للأسرار** في `prod`. غيابها يوقف الإقلاع.
3. `.env` للتطوير فقط، **خارج Git**. و`.env.example` في Git **بلا قيم حقيقية**.
4. في الإنتاج تأتي المتغيرات من **منصة النشر** (أو ملف بصلاحيات مقيّدة)، لا من الصورة.
5. التطبيق يتحقق من الإعدادات عند الإقلاع ويفشل بوضوح (`check-config`).

### 4.3 توليد الأسرار

| السر | الطريقة |
|---|---|
| `SECRET_KEY` و`IP_HASH_SALT` | `openssl rand -hex 32` (أو `python -c "import secrets; print(secrets.token_hex(32))"`) |
| `TOTP_ENCRYPTION_KEY` | `python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"` |

**قواعد:** قيمة **مختلفة** لكل بيئة (dev / staging / prod). لا تُرسَل عبر واتساب أو البريد. وتُحفظ نسخة منها في **مدير أسرار** أو مكان مشفّر، لأن فقدان `TOTP_ENCRYPTION_KEY` يعني فقدان أسرار MFA كلها.

### 4.4 مواصفات `.env.example`

يحوي **كل** المتغيرات أعلاه، بقيم **توضيحية** (`change-me`) وتعليقات، ولا يحوي أي سر حقيقي. ويُحدَّث مع كل متغير جديد (بند في تعريف الاكتمال، `05` القسم 20).

## 5. حاويات التطوير (Docker Compose)

### 5.1 الخدمات

| الخدمة | الصورة | الاستعمال |
|---|---|---|
| `db` | PostgreSQL 16 | قاعدة التطوير |
| `db_test` | PostgreSQL 16 | قاعدة الاختبارات (منفصلة، تُفرَّغ) |

### 5.2 مقتطف مرجعي

```yaml
services:
  db:
    image: postgres:16
    environment:
      POSTGRES_DB: bloodday
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: dev-only-password
    ports: ["5432:5432"]
    volumes:
      - db_data:/var/lib/postgresql/data
      - ./scripts/db/init-roles.sql:/docker-entrypoint-initdb.d/10-roles.sql:ro
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres -d bloodday"]
      interval: 5s
      retries: 10

  db_test:
    image: postgres:16
    environment:
      POSTGRES_DB: bloodday_test
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: dev-only-password
    ports: ["5433:5432"]
    tmpfs: ["/var/lib/postgresql/data"]   # يُمحى عند الإيقاف، أسرع للاختبار

  mail:
    image: axllent/mailpit
    ports: ["8025:8025", "1025:1025"]

volumes:
  db_data:
```

> كلمات المرور هنا **للتطوير فقط** ولا تُستعمل خارج الجهاز المحلي.

### 5.3 مواصفات `Dockerfile` (للإنتاج)

| البند | القرار |
|---|---|
| **بناء متعدد المراحل** | مرحلة بناء (تثبيت الاعتمادات من القفل) + مرحلة تشغيل نحيفة |
| **الاعتمادات** | من ملف القفل فقط، **بلا اعتمادات التطوير** |
| **المستخدم** | غير جذر |
| **الأسرار** | **لا تُنسخ** إلى الصورة (لا `.env`) |

## 6. قاعدة البيانات

### 6.1 الأدوار (تنفيذ `02`، القسم 7)

يُنشأ دوران قبل أول هجرة (سكربت `scripts/db/init-roles.sql` للتطوير، ويدويًا أو عبر المنصة في الإنتاج):

| الدور | الصلاحيات |
|---|---|
| **`app_migrator`** | يملك المخطط، ينشئ الجداول ويعدّلها (الهجرات فقط) |
| **`app_user`** | `SELECT/INSERT/UPDATE/DELETE` على الجداول، و`USAGE` على المتسلسلات. **بلا DDL** |

```sql
-- مرجعي: أدوار بلا صلاحية superuser
CREATE ROLE app_migrator LOGIN PASSWORD '...';
CREATE ROLE app_user     LOGIN PASSWORD '...';

GRANT CONNECT ON DATABASE bloodday TO app_migrator, app_user;
GRANT ALL ON SCHEMA public TO app_migrator;
GRANT USAGE ON SCHEMA public TO app_user;

-- صلاحيات افتراضية لما ينشئه app_migrator مستقبلًا
ALTER DEFAULT PRIVILEGES FOR ROLE app_migrator IN SCHEMA public
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO app_user;
ALTER DEFAULT PRIVILEGES FOR ROLE app_migrator IN SCHEMA public
  GRANT USAGE, SELECT ON SEQUENCES TO app_user;
```

**وتضيف الهجرة 008** (`02`، القسم 12.2) تقييد `audit_log`: سحب `UPDATE` و`DELETE` و`TRUNCATE` من `app_user` (BR-AUDIT-02).

### 6.2 القواعد
- كلمات مرور الدورين **مختلفة**، وفي الإنتاج **قوية وفريدة** وفي مدير أسرار.
- `DATABASE_URL` يستعمل `app_user`، و`MIGRATION_DATABASE_URL` يستعمل `app_migrator`.
- حاوية التطبيق الدائمة **لا تحمل** `MIGRATION_DATABASE_URL`؛ تُنفَّذ الهجرات في **خطوة نشر منفصلة** (القسم 11).
- في الإنتاج المُدار: اتصال مشفّر (`sslmode`)، وقيد شبكي يسمح للتطبيق فقط.

### 6.3 الهجرات (Alembic)

| الأمر | الاستعمال |
|---|---|
| `uv run alembic upgrade head` | تطبيق كل الهجرات |
| `uv run alembic downgrade -1` | تراجع خطوة |
| `uv run alembic revision --autogenerate -m "وصف"` | توليد هجرة (**تُراجَع يدويًا**) |
| `uv run alembic current` / `history` | الحالة والتاريخ |
| `uv run alembic check` | هل النماذج متطابقة مع الهجرات؟ |

قواعد العمل مع الهجرات في `02`، القسم 12.1 (لا تعديل لهجرة طُبّقت، ومراجعة التوليد التلقائي، ونسخة احتياطية قبل الإنتاج).

## 7. أوامر CLI

تُشغَّل: `uv run python -m app.cli <أمر>` (أو داخل الحاوية: `docker compose run --rm app python -m app.cli <أمر>`).

| الأمر | الوظيفة | ملاحظات |
|---|---|---|
| `create-admin` | إنشاء أول أدمن (أو طارئ) | يسأل عن البريد والاسم وكلمة المرور **تفاعليًا**، ولا تُمرَّر في سطر الأوامر. وبعد أول دخول يُلزَم بتفعيل MFA |
| `seed` | بيانات تجريبية (`02`، القسم 14) | **يرفض العمل إذا `APP_ENV=prod`** |
| `purge` | الإخفاء بعد سنة + تنظيف السجلات والرموز والجلسات | آمن التكرار. **`--dry-run`**: يعرض ما سيفعله دون تنفيذ *(إضافة مقترحة على قائمة `05`)* |
| `deactivate-supervisors` | تعطيل جماعي للمشرفين | بعد الحملة |
| `check-config` | يتحقق من المتغيرات والاتصال بالقاعدة والتخزين والبريد | قبل أي نشر، ويُرجع رمز خروج غير صفري عند الفشل |
| `unlock-user <email>` | فك قفل طارئ | عند غياب الأدمن (يتطلب وصولًا للخادم) |

**قواعد:** الأوامر تستدعي **الخدمات نفسها** (لا منطقًا مكرّرًا)، وتسجّل أحداثها في التدقيق بـ`actor` فارغ، ولا تطبع بيانات شخصية.

## 8. تشغيل الاختبارات

### 8.1 الإعداد
1. تشغيل `db_test`: `docker compose up -d db_test`.
2. ضبط `APP_ENV=test` ومتغيرات `TEST_DATABASE_URL` (لقاعدة الاختبار فقط).
3. الاختبارات **ترفض العمل** إن كان `DATABASE_URL` يشير إلى قاعدة غير الاختبار (حماية من مسح بيانات حقيقية).

### 8.2 الأوامر

| الغرض | الأمر |
|---|---|
| كل الاختبارات | `uv run pytest` |
| الحرجة فقط (★) | `uv run pytest -m critical` |
| طبقة محددة | `uv run pytest -m "unit"` أو `db` أو `api` أو `security` |
| قاعدة عمل واحدة | `uv run pytest -m "br" -k "br_donor_09"` |
| بلا البطيئة | `uv run pytest -m "not slow"` |
| التزامن والهجرات | `uv run pytest -m "slow"` |
| التغطية (مساعد) | `uv run pytest --cov=app` |

### 8.3 قواعد
- لا بيانات حقيقية في أي اختبار.
- لا اتصال بخدمات خارجية (البريد والتخزين والوقت مزيّفة).
- بوابات CI في `07`، القسم 10.

## 10. معمارية واجهة الويب والأصول (Jinja2)

> حُسمت معمارية الواجهة في **D-34** و **D-71** و **D-73**:

| البند | القاعدة المعتمدة |
|---|---|
| **النمط** | قوالب **Jinja2 خادمة** + وحدات JavaScript خفيفة بدون خطوة بناء ولا SPA |
| **النطاق الموحد** | التطبيق نفسه يخدم الصفحات على الجذر (`/`) وواجهة الـ API تحت `/api/v1` (قرار D-73) |
| **في التطوير** | **لا خادم منفصل للواجهة ولا dev proxy**. أمر `uvicorn app.main:app --reload` يخدم الصفحات وقوالب HTML والـ API معًا |
| **الأصول الثابتة** | مستضافة ذاتيًا محليًا داخل `app/web/static/` وتُخدم على المسار `/static` (لا CDN ولا خطوط خارجية، قرار D-71) |
| **سياسة أمان المحتوى (CSP)** | تقتصر السكربتات والأنماط على نفس الأصل (`script-src 'self'`)، ويُمنع أي سكربت مضمّن (`inline script`) منعًا باتًا |
| **الكوكي و CSRF** | تعمل الكوكي تلقائيًا على النطاق الموحد (`SameSite=Lax`)، والصفحات تدمج رمز CSRF في نماذج JS عبر وسم meta أو رأس الطلب |
| **الأخطاء في الواجهة** | ملف ترجمة مركزي في `app/web/static/js/` يترجم `error.code` القادمة من الـ API إلى الرسائل العربية المعتمدة (`04` §3.3) |
| **فهرسة محركات البحث** | وسم `noindex, nofollow` إلزامي على صفحات `/emergency` و `/supervisor` و `/admin` |

# الجزء الثاني: الإنتاج

## 11. تسلسل النشر (مرجعي)

```
1. بناء الصورة من الفرع الرئيسي + اجتياز كل البوابات
2. نسخة احتياطية من قاعدة البيانات
3. تشغيل الهجرات بدور app_migrator (خطوة منفصلة)
4. check-config على البيئة الجديدة
5. نشر الصورة الجديدة (يُبدَّل الإصدار)
6. فحص /ready ثم فحص الدخان (smoke test)
7. مراقبة الأخطاء لبضع دقائق
8. عند الفشل: التراجع (إعادة الصورة السابقة؛ وهجرة downgrade فقط إن لزم)
```

**قواعد:**
- الهجرات **متوافقة للخلف** حيثما أمكن (إضافة قبل حذف) كي لا يتعطل الإصدار القديم أثناء التبديل.
- **لا هجرة مدمّرة** في آخر 3 أيام قبل الحملة (`10`).
- **تجميد** الهجرات والإصدارات قبل الحملة بأسبوع.

## 12. إعداد الإنتاج

### 12.1 المخطط

```
الإنترنت
   │ HTTPS (443)
┌──▼───────────────┐
│  Caddy (وسيط)     │  HTTPS تلقائي، ترويسات الأمان، الملفات الثابتة
└──┬────────────┬──┘
   │ /api       │ /media (إن كانت الصور محلية)
┌──▼────────┐  ┌▼────────────┐
│ app (حاوية)│  │ قرص الصور    │
└──┬────────┘  └─────────────┘
   │ TLS
┌──▼───────────────┐
│ PostgreSQL مُدار  │  نسخ احتياطي تلقائي
└──────────────────┘
```

### 12.2 الوسيط العكسي (Caddy، مرجعي)

| الوظيفة | التفصيل |
|---|---|
| **HTTPS** | تلقائي (شهادات تُجدَّد تلقائيًا) |
| **المسارات** | `/api/*` ← التطبيق. `/media/*` ← الصور. غير ذلك ← الواجهة الثابتة |
| **ترويسات الأمان** | `Strict-Transport-Security`، `X-Content-Type-Options: nosniff`، `Referrer-Policy`، منع التضمين، و`Content-Security-Policy` مناسبة للواجهة |
| **ترويسة العنوان** | يمرّر `X-Forwarded-For` للتطبيق، **والتطبيق يثق بها فقط من عنوان الوسيط** (`TRUSTED_PROXIES`) |
| **حدود الجسم** | أقصى حجم طلب (يتسع للصور 5 ميغابايت) |
| **الضغط** | مفعّل للنصوص |
| **السجلات** | بلا بيانات حساسة في الروابط (لا هاتف في المسار، `04`) |
| **`/docs`** | محجوب في الإنتاج |

```caddy
# مرجعي للإنتاج (Caddyfile):
# bloodday.example {
#     encode gzip zstd
#     handle /static/* { root * /app/app/web/static; file_server }
#     handle /media/* { root * /srv/uploads; file_server }
#     handle { reverse_proxy app:8000 }
# }
```
#     header { Strict-Transport-Security "max-age=31536000"; ... }
# }
```

### 12.3 خادم التطبيق

| البند | القرار |
|---|---|
| **الأمر** | Gunicorn مع عامل Uvicorn (أو Uvicorn مباشرة بعملية واحدة) |
| **العمليات (workers)** | **عملية واحدة** في النسخة الأولى (يكفيها المجمّع الخيطي للتطبيق التزامني)، فيبقى محدد المعدل في الذاكرة سليمًا |
| **الخيوط** | مجمّع الخيوط الافتراضي، ويُضبط عند الحاجة |
| **مجمّع الاتصالات** | `DB_POOL_SIZE + DB_MAX_OVERFLOW` ≤ حد الاتصالات في الخطة المُدارة |
| **المهلة** | معقولة (مثل 30 ثانية) |
| **إعادة التشغيل** | تلقائية عند الفشل (سياسة الحاوية) |
| **الذاكرة والمعالج** | صغيران (التطبيق خفيف)؛ وتُراقَب |

### 12.4 عند الحاجة لعدة عمليات
محدد المعدل في الذاكرة **لا يتشارك** بين العمليات. عند التوسع: تفعيل `RATE_LIMIT_BACKEND=db` (يتطلب جدول `rate_limit_events` يُضاف إلى `02`) أو Redis. وفي **كشف أرقام الطوارئ** الحد الفعلي مدعوم أصلًا بجدول `phone_reveal_log` في القاعدة (فهو لا يتأثر بإعادة التشغيل).

### 12.5 الصور
- **قرص مُركَّب دائم** (volume) للمسار `STORAGE_LOCAL_PATH`، أو **مخزن كائنات** (`s3`).
- **النسخ الاحتياطي للصور** منفصل عن القاعدة، ويخضع لسياسة الحذف (`file_deletion_queue`).
- حذف ملفات الطابور: أمر دوري أو يدوي (D-06/`02`).

### 12.6 المهام المجدولة

| المهمة | الأمر | التكرار |
|---|---|---|
| الإخفاء والتنظيف | `purge` | شهريًا (ويُجرَّب بـ`--dry-run` أولًا في المرة الأولى) |
| نسخ احتياطي للقاعدة | حسب المنصة المُدارة + `pg_dump` يدوي قبل الحملة وبعدها | يوميًا + يدوي |
| حذف ملفات الطابور | أمر أو يدوي | أسبوعيًا |

**التنفيذ:** `cron` على المضيف أو مجدول المنصة يستدعي الأمر داخل حاوية مؤقتة (`docker compose run --rm app python -m app.cli purge`). ويُراقَب نجاح المهمة (رمز الخروج وإشعار عند الفشل).

### 12.7 الشبكة والأمان
- منفذا **80/443** فقط مفتوحان للعامة. التطبيق والقاعدة **غير مكشوفين** مباشرة.
- قاعدة البيانات المُدارة تقبل اتصالات من عنوان التطبيق فقط.
- جدار ناري على المضيف، وتحديثات أمنية للنظام.
- الدخول إلى الخادم بمفاتيح SSH فقط، بلا كلمات مرور.
- الأسرار في متغيرات المنصة أو ملف بصلاحيات `600` خارج المستودع.

## 16. استكشاف الأخطاء

| العَرَض | السبب المحتمل | العلاج |
|---|---|---|
| `/ready` يفشل | القاعدة غير متاحة أو `DATABASE_URL` خطأ | فحص الاتصال والدور وكلمة المرور و`sslmode` |

| الإقلاع يفشل: "secret missing" | سر غير مضبوط في `prod` | ضبطه (القسم 4.3) |
| رفض رفع صورة صالحة | `MAX_UPLOAD_BYTES` أو حد الوسيط | مراجعة الحدين |
| الصور لا تظهر | `STORAGE_PUBLIC_BASE_URL` أو مسار الوسيط `/media` | فحص الإعداد والصلاحيات على المجلد |
| الدعوات لا تصل | SMTP خاطئ أو السجلات المرفوضة | `check-config`، واختبار SMTP، ومراجعة السبام |
| اتصالات القاعدة تنفد | `DB_POOL_SIZE` × العمليات > حد الخطة | تخفيض الحجم أو العمليات |
| الاختبارات تمسح بيانات التطوير | `DATABASE_URL` يشير للقاعدة الخطأ | حماية القسم 8.1، وفصل المتغيرات |

## 18. ملخص

- **التشغيل المحلي في خطوات واضحة:** `uv sync` ← `.env` ← قاعدة الحاوية و Mailpit ← الهجرات ← `create-admin` ← `seed` ← خادم uvicorn الموحد.
- **لا خادم منفصل للواجهة:** تطبيق FastAPI يخدم صفحات Jinja2 والـ API والأصول الثابتة معًا في التطوير والإنتاج.
- **الإعدادات من البيئة فقط**، والأسرار بلا قيم افتراضية في الإنتاج، و`check-config` يفحصها عند الإقلاع.
- **مفاتيح إيقاف الطوارئ والتعهدات** مدعومة عبر متغيرات البيئة لتعطيلها الفوري بـ `503`.
- **دوران في قاعدة البيانات:** `app_migrator` للهجرات، و`app_user` للتشغيل بلا DDL، وقاعدة اختبار منفصلة `TEST_DATABASE_URL` على tmpfs.
- **الإنتاج:** Caddy وسيطًا (HTTPS تلقائي)، وعملية واحدة للتطبيق، وقاعدة مُدارة، وصور على قرص مُركَّب دائم.
